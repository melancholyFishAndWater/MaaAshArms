# 测试职责与重构边界

测试应约束需要保持的行为，不逐项复制当前实现。结构调整后先判断业务契约是否改变，再决定改生产实现还是测试；不能仅因为测试报错就把期望改成当前返回值。

## 三层职责

| 层次 | 约束内容 | 不应绑定 |
| --- | --- | --- |
| 业务结果 | 给定输入与状态的决策、完成判据、跨天、持久化、失败回滚 | 内部函数名称、调用次数、数据成员布局 |
| 框架适配 | MaaFW 返回值形状、节点覆写目标、注册与调用参数、明确的失败处理策略 | 与适配契约无关的内部调用顺序 |
| 结构与资源 | 必要能力可达、影响行为的候选相对顺序、关键动作类型；引用和 Schema 交给现有校验器 | 完整 `next` / `all_of` 列表快照、注释文案、非必要显示通道 |

业务结果测试使用明确的输入/期望表；框架适配测试单独验证必要副作用。相同副作用不要在每个业务用例重复断言。结构测试只做本任务所需的局部图检查，不实现 pipeline 执行模拟器，不假装离线测试证明识别和点击在真机成功。

启动链的例子：已在游戏内的停止判断必须早于启动应用；登录后的主页检查必须早于重试自环。允许插入合法辅助节点，允许公告关闭经过中间节点，失败提示可选择受支持显示通道。And 条件只在组合契约要求时检查成员或顺序；依赖首项落框的行为若改变，仍须框架适配或真机证据确认。

## 何时调整契约

- **纯重构，用户可见行为不变**：保留业务期望；消除只约束旧实现形状的断言。若节点覆写策略本身有明确需求，适配测试仍保留。
- **需求明确改变**：先写明新的输入、预期结果、边界和原因，再同步生产与测试。不能从实现自动生成预期。
- **框架接口或资源协议改变**：核对上游语义，更新适配/资源测试，不自动放宽业务结果。
- **失败原因不清楚**：保留失败并定位；禁止用无条件 `xfail`、`skip`、删掉全部断言或排除失败文件使 CI 变绿。

高价值契约应有反例验证：在合成配置中破坏关键顺序或移除必要能力，复用同一个断言 helper 确认测试拒绝；同时验证合法插入不会误报。反例不能另写一套“正确算法”与被测逻辑互相证明。

本次分层优化以 Store/Daily 与启动链测试为示范；其余既有测试尚未逐个迁移，后续在对应需求或重构中按这些原则复核，不要求为统一形式批量改写。

## 本地运行与交付

```powershell
uv run --locked python -m pytest -q tests
# 完整 CI 对齐检查与工具门禁
uv run --locked python tools/validation/cli.py preflight
# 或
npm run check:all
```

完整工作流用法见 [校验说明](../tools/validation/README.md)。专项测试用于缩小反馈周期，不能代替交付前的完整 preflight；失败、跳过和环境限制必须如实报告。设备相关修改另做真机验收。

修改已有测试脚本遵循仓库的同目录副本约定；验证副本时使用 `pytest --import-mode=importlib`，通过后替换，再对正式文件复跑。
