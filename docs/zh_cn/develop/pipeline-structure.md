# 任务链结构

版本号: v4.0

**v4.0 变更**：自环重试采用有限 `max_hit` 与结构条件清零；删除工作循环分类及其旧写法。
`BaseErrorNext` 的移除和存量自环节点补充 `max_hit` 留待未来逐步进行，本次不批量迁移 pipeline。
校验器与自环模板已同步；存量迁移说明见「〇」节。

本文约定一个任务从入口到页面循环怎么搭：每类节点放在哪、谁负责动作、`[JumpBack]` 和 `max_hit` 怎么算。加新任务或拆现有任务链时按本文搭。

命名规则（动词、前缀、`Probe` / `Branch`）见 [节点命名与分类](./node-naming.md)。

**第十节「识别预算」**：页面导航用 `Branch` 平铺；单探针内联。

## 〇、节点层拼法：自环重试 + `max_hit` + 分支

角色由结构决定，不由 `desc` 标记决定。

| 角色 | 结构判据 | 职责 |
| --- | --- | --- |
| 探测 | 有 `recognition`、无 `action`、无 `next` | 判断当前页面或状态 |
| 分支 | 有 `recognition`、有 `next`、无 `action` | 按状态派发候选 |
| 动作 | 有 `action`，可有 `next` | 执行动作；`next` 含自身时为自环动作 |

### 自环重试与命中计数重置

自环重试节点配置有限 `max_hit`，同时保留正常出口与有限 `timeout`。框架的命中次数按节点名存储，
在整个 task 及共享状态的子任务中累计；自环节点的计数由 Agent 的 `BaseHitResetSink` 按下列条件清零：

1. 收到识别成功事件，且命中节点不是当前派发者自身；自身命中不清零。
2. 当前候选列表包含派发者自身，即派发者是自环节点。
3. 命中候选不是 `[JumpBack]` 引用，或者是 `[JumpBack]` 引用且命中节点自己的有效 `next` 非空。

满足条件时，调用 `context.clear_hit_count(派发者名)`；清的是父节点，不是刚命中的候选。
`[JumpBack]` 按本轮引用属性判断，不按节点名或 `desc` 标记判断。无需维护显式节点名单，
也不按父节点切换清零。实现见 `agent/shared/generic.py` 的 `BaseHitResetSink`。

这套策略限制连续自环重试，不保证每次清零都代表业务完成，也不限制多节点往返循环。
无 `next` 的 jp 叶子命中不清父节点计数，但也不会增加父节点计数，因此不受父节点 `max_hit` 限制。
不统一要求 jp 叶子配置 `max_hit`；需要限次时按实际用途单独处理。

`max_hit` 耗尽只会跳过该候选，不会立即报错，也不会直接触发它自己的 `on_error`。
后续候选仍可接管；都不命中时，通常等当前派发者的 `timeout` 后走其 `on_error`。
候选列表存在无条件成功收尾时，耗尽也可能变成成功，不能把“加了 `max_hit`”当成失败保障。

### 自环动作的写法

```json
"<前缀><动词><宾语>": {
    "desc": "…",
    "recognition": "TemplateMatch",
    "template": "<任务目录>/<按钮模板>.png",
    "action": "Click",
    "max_hit": 10,
    "post_wait_freezes": 1000,
    "next": [
        "<前缀><下一步>",
        "<自己>"
    ]
}
```

`10` 是重试预算示例，不是所有节点的统一上限。按实际耗时与正常加载过程确定预算；首次进入也计一次。
单消费者探针按第十节内联；多条件 `And` 保留独立命名的子识别。

自环动作必须有正常离开当前步骤的候选，并检查额度耗尽后的接管路径。
`timeout` 只限制当前候选轮询一直无命中的等待；自环或 jp 子链持续命中时，它不限制循环总时长。
一次性初始化与业务总次数仍按其原有语义配置 `max_hit`，不能把需要累计的业务次数放在自动清零的自环上。

### `[jp]` 节点不许自环

`desc` 带 `[jp]` 表示单次执行后交还调用方，不代表整个 task 只能命中一次。
它自身的 `next` 不许包含自己（`A20-jp-self-loop`）；需要自环重试时去掉 `[jp]` 标记。
引用处也不使用 `[JumpBack]自身`。

### `BaseErrorNext` 的过渡期

`BaseErrorNext` 仍由 `BaseErrorNextReco` 按派发者累计评估轮数，旧 `_BaseErrorNextSink` 按结构策略清零。
满 10 轮时合成 `<父节点名>ErrorNext`、覆写父节点的 `next`，由合成节点执行失败动作。
它的字典计数与框架 `hit_count` 是两套独立状态，新 sink 不会停用旧机制。

未来按任务逐步为自环重试节点补充 `max_hit`，核对清零条件、正常出口、耗尽后的候选接管和超时路径，
再移除对应的 `BaseErrorNext` 引用；不因更新规范就批量删除引用或旧实现。
仍依赖它保护 jp 重试的列表单独评审，不能假定父节点的 `max_hit` 已覆盖 jp 持续命中。

校验器 `A21-self-loop-without-max-hit` 提示自环缺少有限 `max_hit`；它不证明无限循环，也不推演动态覆盖和耗尽后的接管。
旧 `BaseErrorNext` 引用不能豁免 A21；存量缺预算的 warn 留待未来按任务逐步处理。
保留的 `BaseErrorNext` 仍排 `next[0]`（A22），以免前面的命中候选阻止旧计数。

`BaseBranchError` 继续负责挡路弹窗，按第九节安排位次；它与重试计数是不同职责。

### 注释口径（可读性，非运行时）

节点前的注释写什么，跟"这个节点是不是主干"有关：

+ **主干节点**（有 `next` 的：动作、分支、任务入口）前面要写注释，说明这个节点做什么。注释必须紧挨着节点，中间不能隔别的节点。
+ **纯辅助节点**（没有 `next`，如 `EscortClickDeliveryButton`、`BaseClickHomeButton`、`BaseMoveUp`）不要求写注释——它们是跟着引用它们的节点一起读的，逐个加注释只会把文件撑长。
+ **分节头保留大类型**：`/* ---- 动作-进入一览 ---- */`、`/* ---- 分支-主页面 ---- */` 只写类别与页面名，不写整句说明；类别用 `动作-` / `分支-` 这类大类型，后面跟页面名。
+ **行内 `//` 注释 4~6 字**：写页面名或动作名（`// INFO 点击箭头`、`// INFO 奖励页面`），不写长句、不复述 `desc`。
+ **陷阱提示放进相关节点内部**：滑动起点落在物品上、某个模板在弹窗下仍会命中这类提示，写在该节点自己的注释里，不堆在文件头或分节头。
+ 分节注释（`/* ---- 探测 ---- */` 这种带横线的）下面紧跟的必须是动作 / 分支 / 任务入口；`/* ---- 通用探测 ---- */` 下面允许是 `Probe`；非通用 `Probe` 放到用到它的节点后面，先看到"谁在用它"再看到它本身，读起来才顺。

文件头部那种多行 INFO 注释（写版本注解的）不算分节注释，不在此列。

## 一、入口、探测、分支与动作

「〇」节是**节点层面**的拼法；本节是**链层面**的分层。

```text
TaskX            入口：门控、初始化、选择"去哪"
  ├── XProbeY    探测：只读，回答"在不在 Y"
  ├── XBranchY   分支：在 Y 就把 next 交出去
  └── XClickY    动作：执行一步并等待后续状态
```

| 层 | 只回答 | 允许出现在 `next` 里 |
| --- | --- | --- |
| 探测 `<前缀>Probe<对象>` | 现在是不是在对象上 | 无 `action`、无 `next`（命中即终点） |
| 分支 `<前缀>Branch<状态>` | 这个状态成不成立 | 该状态下的工作候选、`[JumpBack]` 兜底（命中即转，不保证页面） |

分工的判据是**谁改页面**：只有动作节点可以点入口，`Branch` 只判页面、把 `next` 交出去。这样探测节点保持只读、幂等，可以安全地并排放进任何 `next`；动作是否重试由识别、出口与预算共同决定。

页面导航的"点入口"由**动作节点**做，它自己带 `next` 等待结果；自环重试按「〇」节配置预算；点不动时补一刀的语义，由 `next` 里再排一个更宽松判据的动作节点表达。调用方只看到"在 A 页就做 A、不在就试下一个 `Branch`"，不再有封装的就位节点。

`TaskX.next` 里的 `Init` 类节点分两种（判据见第八节「`Init` 的两类」）：写全局变量、读参数、清计数的真初始化放前段（`ProbeDaily` 之后）合理；本质是"先取一次状态再写全局"的，按探测命名，位置交给调用它的 `Branch` 决定，不要顶在 `next` 第一位挡住后面的候选。

## 三、页面内工作与动作重试

页面内工作由 `Branch` 派发动作或子流程，不再设置独立的工作循环类别。
多段工作需要完成后返回父列表时，在引用处使用 `[JumpBack]`。

动作的识别判断是否可以执行；后续候选判断是否生效或应转到其他步骤。
自环重试按「〇」节配置 `max_hit` 与计数重置；不强制要求动作执行后立刻不再命中，
因为同帧加载仍可能重复识别到原状态，预算需要覆盖正常重试。

`[JumpBack]` 返回只重扫父节点的 `next`，不重新执行父节点的识别与动作。
因此不能把父 `Branch` 的识别当作每轮都会重跑的页面守卫；完成、离开页面或失败后的状态
必须有相应候选接住。候选全未命中最终属于超时失败，不等价于正常完成。

## 四、`[JumpBack]` 放在哪

`[JumpBack]` 标的是**引用处**，不是节点属性。同一个节点在 A 处是候选位、在 B 处可能是顺序位，两者都对：

### jp 栈：命中压父节点、走到头弹栈

`[JumpBack]`（jp）在框架里对应一个 jumpback 栈：

1. 某个 jp 节点**命中**时，把**父节点**压栈（push 发生在它的动作执行之前，动作失败也不撤销）；
2. 命中节点跑完自己的 `next`、**没有下一步可走**（`next` 为空，且当前不在错误处理里）时，
   弹栈一个元素，继续遍历它的 `next`——不重跑它的识别与 action；
3. 栈里没有元素 → 任务正常结束（判成功）。

所以 jp 链的语义是"先把这段干完，再回到调用方继续"；"命中且没 jp 可走"的那一步由栈决定，
不要靠给节点补 `next` 来模拟弹回。明细（push/pop 的条件、失败时弹回被跳过）见
`.agents/maaframework.md` 的「next 分发与 JumpBack」。

| 位置 | 含义 | 该不该标 |
| --- | --- | --- |
| 候选位 | "这件事必须先办成，办完弹回我这里继续" | 必须标 |
| 顺序位 | "顺手往下走，不在我就试下一项" | 不标 |

四条落地规则：

1. **回上级 / 回枢纽一律当候选位**：`[JumpBack]BaseReturnHome`、`[JumpBack]<入口动作>`、`[JumpBack]BaseBranchError` 这类引用都写 `[JumpBack]`。这类节点跑完要弹回调用方的 `next`，由调用方决定下一步；它自己不许串到别的任务的主循环。
2. **页内进入（入口动作 → 工作分支）是顺序位**，不标 `[JumpBack]`，靠 `next` 自然遍历过去。
3. **同任务内可以 `[JumpBack]` 指向子 `Branch` 或动作子流程**：先完成子流程，再返回调用方继续。
   禁止指向自身、通过回跳反复进入祖先流程，或串到别的任务的主循环。
4. jp 叶子只执行一步就交还调用方；带 `next` 的 jp 节点执行整段子流程再返回。不要为了限次把两者混为一类。

## 五、预算

+ **自环重试**：有限 `max_hit` 配合「〇」节的结构条件清零，限制连续自环命中。
+ **一次性或业务限次**：`max_hit` 按整个 task 累计，额度耗尽只跳过候选；必须确认用尽后由谁接管。
+ **jp 通用动作**：不统一要求 `max_hit`，不按调用方变化自动重置；共享节点的额度与计数读取用途须单独核对。
+ **有限 `timeout`**：限制当前派发者的一次候选轮询无命中等待，不限制持续命中的自环或 jp 循环。
  入口的大 `timeout` 管不到下游，jp 返回后也会重新开始父列表的轮询预算。
+ **失败与收尾**：`on_error` 只放必须的收尾；没有收尾需求可留空，让超时或动作失败正常报告失败。
  无条件 `StopTask` 不是失败兜底，不用它掩盖候选耗尽。
+ **持续等待**：`timeout: -1` 仅用于明确需要持续等待且有真实退出条件的流程，并注明业务意图。
+ **存量迁移**：`BaseErrorNext` 的未来移除范围与验收要求见「〇」节；本轮不批量补次数或删除引用。

## 六、命名对应

| 类别 | 命名 |
| --- | --- |
| 探测 | `<前缀>Probe<对象>` |
| 分支 | `<前缀>Branch<状态>` |

`Probe` / `Branch` 后面的对象是页面或状态的短名，与 `Probe` 用的一致（`TrainingProbeHome` / `TrainingBranchHome`）。页面导航需要的动作节点仍按动词表命名（`EnterBattleMainPage`、`ClickConfirm` 等）。

## 七、等次与枢纽

+ 页面之间不是平级的：**枢纽页**（大厅、出击页）被多个任务共用，**等次页**（训练所、维修会、订单工厂、赠礼）只服务自己那条链。
+ 从等次页回到枢纽是"降级"，用 `[JumpBack]BaseReturnHome`（或调用方 `next` 里的回枢纽 `Branch`）表达；从枢纽进等次页是"进入"，用入口动作节点。
+ 回枢纽的兜底（`BaseReturnHome`、`[JumpBack]BaseBranchError`）不许串到任何任务的主循环——它只负责"把人送回去"，去向由调用方的 `next` 决定。

## 八、待斟酌（写清判据，不做成校验规则）

### 出口节点是否匹配画面

`Custom` 识别返回的框决定了链往哪走，但"这个出口是否真的覆盖了画面上的分支"**没有静态判据**：同一个 `Custom` 识别在不同帧可能返回不同结果，工具只能看到"注册名有没有人用、名字对不对"。所以工具侧只保留两条能查的：注册名与节点名一致（`A3`）、注册名被引用（`A2`），其余靠人工。用 `Custom` 当页面判据或分支出口时，至少在注释里写清"返回什么代表什么"（形态选哪个见第三节「页面内工作与动作重试」）。相关：`A13-verb` 只能判"名字里有没有动词"，判不了"动作语义对不对"。

### `Init` 的两类

| 类型 | 特征 | 位置与命名 |
| --- | --- | --- |
| 真初始化 | 写全局变量、读参数、清计数（`TrainingInitAct` 读 `attach`、`ReplaysInitAct` 写 `_max_count`） | 放 `Task.next` 前段（`ProbeDaily` 之后）合理，`max_hit: 1` 也是对的 |
| 取状态再初始化 | 先识别一次状态再写全局（`TrainingGetStatusReco`、`TrainInitReco`） | **本质是探测**，按 `...Probe...` 命名；位置交给调用它的 `Branch` 决定，不要顶在 `Task.next` 第一位挡住后面候选 |

这条只能人工判：一个动作节点到底"只是初始化"还是"顺便取状态"，工具看不出来。落到校验器上的只有 `A4-shadowed-candidate`——它报的是**必然命中且没有 `max_hit`** 的候选：那种每一轮都命中，后面的候选永远轮不到。两类**不报**：**`*Init`**（v3.4，「真初始化」本来就该顶在前段挡一轮）与**带 `max_hit` 的**（v3.7，额度用尽即让位，`EntrustDelegatingReward` 这种 `[jp][once]` 一次性动作就是靠它排在前段先做一次）。

## 九、通用错误分支放哪

`BaseBranchError`（`base.json`）是"点掉挡路弹窗、留一份日志"的通用分支：中央弹窗区（ROI `320,148,636,423`）出现「确认」就命中，先判维护弹窗（`BaseBranchSeverClose` → `StopTask` 并弹通知），否则把弹窗标题与正文写进日志、点掉确认、等画面稳定，再弹回调用方继续。它**不判断"是不是错误"**，所以位置只影响"谁先抢画面"，不影响正常流程的语义。

### 放哪几类节点

只挂在有 `next` 的轮询节点上（`Task` / `Branch` 的候选列表），引用处一律写 `[JumpBack]BaseBranchError`。探测节点与单动作节点没有 `next`，它们的下一轮由调用方列表重新评估，不需要补。

```json
"next": [
    "<目标页正向探针>",
    "[JumpBack]BaseBranchError",
    "[JumpBack]<进入/回撤动作>",
    "<兜底候选>"
]
```

### 位次

四条判据从上往下判，冲突时前一条优先：

| 判据 | 为什么 |
| --- | --- |
| 自家流程会点「确认」的候选排在它**前面** | 同一个「确认」也会命中 `BaseProbeConfirm`；排在前面会抢点，并把正常流程记成"错误弹窗"（例：领奖流程里的"确认转换为零件"） |
| 会把"被压暗"读成状态的候选排在它**后面** | 模态弹窗下按钮模板常常仍命中、只是分数降低；"开始行动变暗＝合金不足"这类判据会被弹窗冒充 |
| 取反守卫（顶层 `inverse: true` 的节点与取反终点探针）默认排在它**后面** | 原识别若受弹窗遮挡而失败，取反候选可能先命中，将"看不见"误读为"不在页面"；须实测原识别是否受遮挡，并确认候选额度及业务优先级，不是必然永久遮蔽 |
| 目标页的正向探针排在它**前面** | 页面正常就直接往下走，不必付这次识别 |

第一条（自己会点「确认」的候选排在 `BaseBranchError` 前面，即 `*Confirm` 在前）v3.2 起由 `A15-error-branch-conflict` 按 **error** 报：确认按钮排到 `BaseBranchError` 之后即违规。

### 不要和专责的停止判断混排

`BaseStopNoMetal` / `IsServerMaintenance` / `IsNetworkError` 是"判到就停"，`BaseBranchError` 是"点掉继续"。两类放在同一列表会互相抢顺序：同一个「确认」既可能被当成错误弹窗点掉，也可能被专责节点判成终止条件。维护弹窗尤其重复——`BaseBranchSeverClose` 与 `IsServerMaintenance` 都是 OCR「维护中」→ `StopTask`，接线时只留一处。

列表里已经有专门点确认的候选（`BaseClickConfirm`、`TrainOverrideConfirm` 这类）时通常不再加：它已经能点掉弹窗，再加只是多一次 OCR。要补的是这类列表之外的入口、页面分支与出口分支。

### 成本

命中评估一次＝一次 OCR（ROI 636×423）。按上表排在正向探针之后，只有前面候选全 miss 才付；排在前面则每轮都付。所以按"入口 + 页面分支 + 会把遮挡读成状态的分支"三处铺，不要每个节点都挂。

### 校验器能查的

`A15-error-branch-jumpback`（引用不带 `[JumpBack]`）、`A15-error-branch-shadowed`（排在取反守卫之后，warn，提示潜在遮蔽而非证明永久不可达）、`A15-error-branch-conflict`（排在自己会点「确认」的候选之前，v3.2 起 **error**）。
shadowed 只查同一候选列表的顺序，不推演截图、额度耗尽后的接管或业务优先级；须用现场图与日志判断，不能批量前移错误分支。
"压暗被误读"那条判不了——哪个模板在弹窗下仍会命中，静态看不出来，按人工。三条触发条件与级别均不变。

## 十、识别预算

一次派发的成本 = **守卫识别**（本节点的 `recognition`）+ **候选识别**（`next` 里被依次评估的项）。失败也要付钱，所以 `next` 的顺序与长度就是预算。

**候选数复核阈值（v3.11 澄清）**：`Task*` 入口**不判**（入口的候选表由人工把关）；其余节点的 `next` > 5 项时报 `A28` warn（v3.10 起；v3.3–v3.9 为 7 项），计长度时不计 `BaseBranchError` / `BaseErrorNext`。
5 项是人工复核阈值，**不是性能分界，也不要求超限就拆 `Branch`**。应结合日志检查各候选的识别成本、实际命中顺序与失败次数，并比较新增守卫、截图及调度轮次的开销；平铺可能比拆分更便宜、更清楚。
`A28` 的触发条件与 warn 级别不变；旧工作循环类别的专属规则已移除。

### 一次派发付几次识别

| 节点形态 | 守卫 | 每个候选 | 说明 |
| --- | --- | --- | --- |
| `DirectHit` | 0 | — | 不识别，白送 |
| `Probe`（单识别） | 1 | — | OCR / TemplateMatch / ColorMatch / Custom 各算 1 |
| `And` / `Or` 组合 | 子项之和（短路） | — | 命中即停，未命中才继续下一子项 |
| 候选是 `And[单探针]` 包装 | 1 | — | 包装本身不额外收费，但多一层事件 |

历史日志样本（16 份日志、28023 次派发）中，`Task` 平均 5.7 次识别、`Branch` 2.9 次；样本值不能替代具体任务实测。

### 页面导航：`Branch` 平铺

页面导航统一用 `Branch` 平铺：每个页面的守卫各写成一个 `Branch`，并列排进调用方的 `next`。`Branch` 命中即转（1 次守卫 + 该页的工作候选），不在就轮到下一个候选；全 miss 时每个候选只付 1 次识别。

平铺写法：

```json
"TaskGift": {
    "next": [
        "[JumpBack]GiftProbeDaily",
        "GiftBranchSortPage",      // 在排序页 → 排序 + 点第一个
        "GiftBranchCharacters",    // 在选择页 → 点好感度
        "GiftBranchHome",          // 在赠礼主页 → 点赠礼
        "[JumpBack]BaseBranchError",
        "[JumpBack]BaseReturnHome"
    ]
},
"GiftBranchSortPage": {
    "recognition": "TemplateMatch",   // 原单探针的识别字段，已按「单探针内联」搬进来
    "template": "Gift/SortPage.png",
    "next": ["GiftChooseFavorability", "[JumpBack]BaseBranchError"]
}
```

每个 `Branch` 只判一个页面、只放该页面的工作候选。不在任何已知页面时依次 miss，落到 `BaseReturnHome`。

**判断顺序**：命中概率高的页面排前面（少付前面的 miss）。这与第九节「错误分支的位次」不冲突——`BaseBranchError` 仍排在正向探针之后。

旧写法 `Ensure` 嵌套（每层固定 5 次识别、靠上一级 `Ensure` 逐级降级）已停用：它换来的只是「再往上退一级」，同样的效果靠调用方 `next` 里多排一个 `Branch` 就能达成，成本是 1 次。

### 单探针内联

只被一处引用的探针把识别写进引用它的节点 `recognition`，删掉 `Probe` 节点；`And all_of [<探针>]` 的单探针包装、`Branch` 的单探针、以及"没有 `recognition` / `action`、`next` 只有这一项"的纯路由同样内联。判据与做法见 [节点命名与分类](./node-naming.md) §3「单探针内联」。

省下的是「多一个节点」的派发与事件开销；多消费者（两处以上引用）保留 `Probe`，它承担的是复用。

**多条件 `And` 不在内联范围**（v3.9）：`all_of` 两个以上条件时，子识别保持独立 `Probe` 节点、按名字引用——命名节点才带得上注册名校验、`box_index` 的落点指认，也好单独复测。校验器 `A26-single-consumer-probe` 只认单探针包装（`all_of` 恰好一项），`A30-and-inline-sub`（warn）专门报多条件 `And` 里的内联对象。

### 首项探针只在守卫会误判时保留

`next` 的首项常常是守卫里那个探针（「刚说不在，再问一遍」）。它的价值是纠正守卫误判，救回率差别很大，**判据：救回率 < 25% 就删掉首项**，把「确认」并进第一个进入动作的 `next`。

救回率必须日志实测，不能凭感觉：在 `maafw.log` 里数这个守卫节点作为派发者时首个候选的 `Node.Recognition.Succeeded` / `Failed` 次数，命中数 ÷ 总数就是救回率。

### 等待也是预算

`post_wait_freezes` / `post_delay` / `rate_limit` 不消耗识别，但占墙钟。实测 69% 的 `wait_freezes` 恰好停在 `time + rate_limit`，说明画面早已静止、等待是纯开销。

| 写法 | 什么时候用 |
| --- | --- |
| `post_wait_freezes` ≤ 1000 | 默认；下一轮候选的探针本身就是「到没到」的判据 |
| `post_wait_freezes` 2000–3000 | 只在页面切换动画确实超过 1 秒时用，并在注释写明是哪个动画 |
| 探针节点上不写 `post_delay` | 探针不改画面，延迟纯属限速；限速用所在 `Branch`的 `rate_limit` |

`rate_limit` 是**每轮识别的最低间隔**，写在 `Branch`上比散在各个探针上更容易核对。

### 校验器能查的

| 规则 | 级别 | 判据 |
| --- | --- | --- |
| `A17-guard-in-next` | info | 节点的 `next` 里含本节点 `recognition` 用到的同一个探针（重复识别） |
| `A20-jp-self-loop` | error | `desc` 带 `[jp]` 的节点，`next` 里含自己（见「〇」节） |
| `A21-self-loop-without-max-hit` | warn | `next` 含自身但没有有限正整数 `max_hit`；静态预算提示，不证明无限循环（见「〇」节） |
| `A22-error-next-not-first` | warn | 引用了 `BaseErrorNext` 但不在 `next[0]`（见「〇」节） |
| `A23-section-comment-probe` | warn | 分节注释下面紧跟非通用 `Probe`（见「〇」节「注释口径」） |
| `A24-node-comment-missing` | warn | 主干节点（有 `next`）前面没有紧挨着的注释；纯辅助节点不要求 |
| `A25-ensure-banned` | warn | 节点名匹配 `Ensure[A-Z]`：v3.1 起 Ensure 类别停用，此节点待删；改用调用方 `Branch` + 入口动作 + `[JumpBack]BaseBranchError`。存量 9 个节点 2026-10-31 已全部删除，`A25` = 0 |
| `A26-single-consumer-probe` | info | 纯探针只被一处引用、且那处是**单探针包装**（`And all_of` 恰好一项）或纯路由：可内联进引用它的节点 `recognition` |
| `A30-and-inline-sub` | warn | 多条件 `And` 的 `all_of` 里出现内联对象：改成独立 `Probe` 节点按名字引用（见「十」节「单探针内联」） |
| `A27-click-ok-banned` | error | 节点名以 `Ok` 结尾：确认按钮统一 `*Confirm`，不许 `ClickOk`（见 [节点命名](./node-naming.md) §6） |
| `A28-next-list-cap` | warn | 非任务入口的 `next` > 5 项（`BaseBranchError` / `BaseErrorNext` 不计入）；人工复核阈值，不强制拆分；`Task*` 入口不判 |
| `A29-and-box-index` | warn | 带 `action` 的节点：`recognition: And` 且 `all_of` > 1 项却没写 `box_index`（取框默认 `all_of[0]`，见「十一」节） |

判不了的：救回率、动画实际时长、哪个候选命中率最高——都要日志实测（`debug/maafw.log` 里的 `Node.NextList.*` / `Node.Recognition.*` / `Node.WaitFreezes.*` 事件流）。

## 十一、`And` 的取框（`box_index`）

`And` 的输出框默认取 **`all_of[0]`**（vendor `deps/tools/pipeline.schema.json` 的 `And.box_index`：「指定输出哪个子识别的识别框…可选，默认 0」，范围 `0 <= box_index < all_of.size`）。`Click` 的落点、`target_offset` 都基于这个框。

组合里各项的框一般不重合，所以"默认 0"是一条**隐式**约定：调整 `all_of` 顺序、或把某个探针换掉，落点就悄悄换了，图上看不出、只有行为变了才发现。

规则（`A29-and-box-index`，warn）：节点**带 `action`**（框会被当落点用）、`recognition: And` 且 `all_of` 多于 1 项时，**显式写 `box_index`**，把意图写清楚：

```json
"TrainEnterHome": {
    "recognition": "And",
    "all_of": ["TrainProbeOverview", "TrainProbeStatus"],
    "action": "Click",
    "box_index": 1,
    ...
}
```

两种不写的情况：

+ **只有 1 项**（单探针包装）——那时 `0` 是唯一可能值。
+ **没有 `action`**（`Probe` / `Branch`）——框只进日志与事件，换个索引没有任何行为差别。
