# 任务链结构

版本号: v2.1

**v2.1 新增**：任务链的基本拼法是「**[Probe + 主动作 + 兜底动作] + 分支**」（详见「〇」节）。原「三层职责」仍保留，但按「四角色」理解：探测、分支、就位（主动作与兜底动作的组合）、工作。

本文约定一个任务从入口到页面循环怎么搭：每类节点放在哪、谁负责动作、`[JumpBack]` 和 `max_hit` 怎么算。加新任务或拆现有任务链时按本文搭。

命名规则（动词、前缀、`Probe` / `Ensure` / `Branch`）见 [节点命名与分类](./node-naming.md)。

**第十节「识别预算」是本版新增**：页面导航优先用 `Branch` 平铺，`Ensure` 嵌套深度上限 2。

## 〇、四角色拼法：Probe + 主动作 + 兜底动作 + 分支

一条任务链由四个角色拼出来，每个角色只回答一个问题。**角色由结构决定，不由 `desc` 标记决定**——判据是「有没有 `action`」「有没有 `next`」「有没有 `recognition`」，静态可查。

| 角色 | 结构判据 | 只回答 | `desc` 标记 |
| --- | --- | --- | --- |
| 探测 | 有 `recognition`、无 `action`、无 `next` | 现在是不是这样 | `[end]` |
| 主动作 | 有 `action`、有 `next` | 正常路径上做这一步，做完往下走 | 无 |
| 兜底动作 | 有 `action`、**无 `next`** | 主动作不生效时补一刀，补完就结束 | `[jp]` |
| 分支 | 有 `recognition`、有 `next`、无 `action` | 这个状态成不成立 | 无 |

四者关系：探测给出"能不能做"的判据，主动作按判据做，兜底动作在主动作没点生效时用更宽松的落点补一次，分支把"当前在哪个页面"分派给对应的候选组。

```text
Task<名>                       入口：门控、初始化
  ├── <前缀>Probe<对象>        探测：只读，回答"在不在"
  ├── <前缀>Branch<状态>       分支：命中就把这组候选交出去
  │     ├── <前缀>Probe<对象>      该页面的判据
  │     ├── <前缀><动词><宾语>     主动作：带 next，往下走
  │     └── [JumpBack]<前缀><动词><宾语>  兜底动作：只补一次
  └── [JumpBack]BaseBranchError 通用错误分支
```

本仓库按这套判据数：探测 110 个、主动作 61 个、兜底动作 100 个、分支形态（`recognition`+`next`+无 `action`）61 个，另有 15 个任务入口（无 `recognition` 也没有 `action`，只有 `next`）。

### 三个角色的边界

- **探测只读**：没有 `action`、没有 `next`，命中即终点。本仓库 110 个结构上的探测节点全部如此（其中 98 个按命名规范叫 `Probe`，另 12 个是历史遗留名，如 `IsFreezes`、`FactoryInHome`）。
- **主动作带 `next`**：`next` 交给"下一步该谁接"，所以它的 `next` 里既有分支、也有兜底动作。
- **兜底动作通常不带 `next`**：它只负责补那一刀，补完就结束，交给调用方的 `next` 继续。带 `next` 的兜底动作不再是"补一刀"而是另起了一段流程——那是另一种合法用法（见下），不是写错。

`[jp]` 只是**约定俗成的标记**，不是角色的判据：本仓库 9 个就位 `Ensure` 节点全部带 `[jp]`，而 100 个结构上的兜底动作里只有 51 个带（`ClickTap`、`BackButton`、`MoveUp`、`TaskStop` 这些通用节点一个都没带）。**判角色看 `action` / `next` / `recognition` 三个字段**，`[jp]` 只用来提示"这个节点是补刀用的"。

### 主动作与兜底动作的配对

兜底动作与主动作配对时，差别只在**判据的宽严**、**落点**和**动作本身**。本仓库 100 个兜底动作里，33 个是被主动作用 `[JumpBack]` 引用、真正当"补刀"用的。按这三项分三种形态：

| 形态 | 例 | 说明 | 数量 |
| --- | --- | --- | --- |
| 完全同形 | `EscortEnterHome` → `[JumpBack]EscortClickHomeButton` | 识别、动作、落点全同，只是再点一次 | 16 |
| 同动作、判据不同 | `ShopEnterHome` → `[JumpBack]ShopClickHomeButton` | 主动作要求 `ShopProbeEnterText` + `BaseProbeHome`，兜底只要前者 | 15 |
| 换了动作 | `TrainingEnterOne` → `[JumpBack]MoveUp` | 兜底做的是另一件事（滑动列表），不是重试 | 6 |

"同动作、判据不同"是最常见的一类：主动作要求"页面对**且**按钮在"，兜底只要求"按钮在"——页面状态没对上时先补一刀，比整个候选表全 miss 强。

"换了动作"的兜底动作名多半不带 `Button` / `Box` 后缀：它的语义是"这一步走不通就换个方式"，不是"再点一次"，写错成重试会一直点同一个东西。

### 兜底动作的引用方式

兜底动作作为**候选位**被引用时，要标 `[JumpBack]`：`[JumpBack]` 弹回调用方的 `next` 重扫，父节点自己的识别与动作不重跑，所以"主动作失败了换兜底"这个语义必须靠 `[JumpBack]` 表达。本仓库 37 处「主动作 → 兜底动作」的引用全部带 `[JumpBack]`。

判据看**引用处**的位置：候选位（"这件事必须先办成，办完弹回我这里继续"）标 `[JumpBack]`；顺序位（"顺手往下走，不在我就试下一项"）不标——`TrainEnsureInfo.next` 里的 `TrainClickArrow` 就是顺序位，不标是对的。完整规则见第四节。

### 兜底动作自己不带 `next`

兜底动作的 `next` 为空是**常规写法**。带 `next` 的有两种情况，都是合法的：

| 写法 | 语义 | 例 |
| --- | --- | --- |
| 无 `next` | 补一刀，补完就结束，交给调用方继续 | `EscortClickHomeButton` |
| 有 `next` | 这一步走不通就把整段子流程重做一遍 | `FactoryCreateOrder`（`next` 含自身，是自循环） |

**哪种对要看那个 `next` 干什么**：它是"下一步该谁接"就写清楚，是"把整段重做"就写清楚（通常 `next` 含自身或指向同一段流程的入口）。静态判不了，按人工看。

### 兜底动作与 `BaseBranchError` 的位次

兜底动作处理"主动作这一下没生效"，`BaseBranchError` 处理"挡路的弹窗"。两者判据不同，位次由第三节第九节「通用错误分支放哪」的判据决定：自家流程会点「确认」的候选排在 `BaseBranchError` 前面，兜底动作属于这一类，排在它前面。

### 探针与主动作的关系

主动作的识别条件通常直接引用探测节点（`recognition: And` + `all_of: [<探针>]`），这样"探测到的东西"和"要点的那个东西"是同一份判据，不会写两遍。兜底动作也可以引用同一个探针——它跟主动作的区别只在判据宽严与落点。

## 一、三层职责

「〇」节的四角色是**节点层面的**拼法；本节是**链层面**的分层。两者对同一批节点从不同角度命名：就位 `Ensure` 是链上的一层，它内部由"主动作 + 兜底动作"实现；探测、分支在两层里都可能出现。

```text
TaskX            入口：门控、初始化、选择"去哪"
  ├── XProbeY    探测：只读，回答"在不在 Y"
  ├── XEnsureY   就位：保证"当前处于 Y"，需要时点入口
  └── XLoop      工作（废弃）：在 Y 里干活，自带页面守卫
```

| 层 | 只回答 | 允许出现在 `next` 里 |
| --- | --- | --- |
| 探测 `<前缀>Probe<对象>` | 现在是不是在对象上 | 无 `action`、无 `next`（命中即终点） |
| 分支 `<前缀>Branch<状态>` | 这个状态成不成立 | 该状态下的工作候选、`[JumpBack]` 兜底（命中即转，不保证页面） |
| 就位 `<前缀>Ensure<对象>` | 怎么让当前处于对象上 | 目标页面的探针、进入动作节点、上一级 `Ensure`、最后一个兜底候选 |
| 工作 `<前缀>Loop`（废弃） | 在对象上干哪些活 | 业务候选、`[JumpBack]` 自愈入口、`[JumpBack]` 回上级、结束判据；新代码用 `Branch` |

分工的判据是**谁改页面**：只有就位层可以点入口。这样探测节点保持只读、幂等，可以安全地并排放进任何 `next`；工作层则可以放心被反复派发。

就位层里的"点入口"由**主动作**做，"点不动时补一刀"由**兜底动作**做——两者都写在就位节点的 `next` 里（兜底动作带 `[JumpBack]`）。所以「〇」节的四角色与本节的三层不冲突：主动作与兜底动作是节点层，探测/分支/就位/工作是链层。

`TaskX.next` 里的 `Init` 类节点分两种（判据见第八节「`Init` 的两类」）：写全局变量、读参数、清计数的真初始化放前段（`ProbeDaily` 之后）合理；本质是"先取一次状态再写全局"的，按探测命名，位置交给调用它的 `Ensure` / `Branch` 决定，不要顶在 `next` 第一位挡住后面的候选。

## 二、就位节点

- 上一级 `Ensure` 只用于"连上级页面都找不到了"的降级，例如从主页一步进出击页失败后回主页重来。
- **嵌套深度上限 2 层**（本版新增，见第十节）：第 3 层往上每多一层多付 5 次识别，改用 `Branch` 平铺到调用方 `next`。
- 复杂页面做不到稳定上一级 `Ensure` 就不要新增 `Ensure`，而是做好动作守卫。
- 就位节点不写业务候选。把工作层的候选塞进就位节点的 `next`，会让同一个节点在"从入口来"和"从工作层自愈来"两种调用下都跑一遍业务，同一轮重复派发。
- `next` 的末项按嵌套与否分两种：**单层 `Ensure`**（服务一个页面、上面就是枢纽那一级）的末项是**最后一个兜底候选**，通常是回主页/枢纽的那一级；**嵌套 `Ensure`** 的末项是上一级 `Ensure`。两者都不点名任何"收尾节点"——嵌套链本质是逐级收缩回主页，结束与否由调用方与守卫决定。

```json
"next": [
    "Probe 节点",
    "Enter 节点",
    "上一层 Ensure 节点"
]
```

## 三、工作循环（v1.9 废弃）

`Loop` 已废弃，职责由 `Branch` 承担：宽守卫圈住页面、收窄候选、守卫失效交还上层。既有 `*Loop*` 节点逐步退役，校验器仍按旧规则报（`A8`/`A10`/`A13-loop-next`/`A14`），退役时间线见 `tools/validation/ISSUES.md`。新代码不要新建 `Loop`。

以下规则仅对既有 `Loop` 节点生效：

- `XLoop` 自带页面守卫（`recognition` 判"还在对象上"）。守卫不成立时弹回调用方。
- 守卫用 `Custom` 时，未命中语义必须是"不在这个页面/状态"，且**必须配有限 `timeout` 作出口**（守卫一直命中时链不会自己结束）。
- `XLoop.next` 自愈序列：先页内入口，再回上级（`[JumpBack]<前缀>Ensure<上级>`）。
- 一页多段独立工作拆成子 `Loop`，由父 `Loop` 用 `[JumpBack]` 串联（第四节规则 3）。

### 哪些活不用 `Loop`

一个动作节点带 `next` 指向自己就是循环，不必再包一层守卫——**能不能这么省，只看退出条件**。

| 形态 | 识别的是 | 点完"生效了没"由谁判 | 卡住的日志 |
| --- | --- | --- | --- |
| 自环动作 | 能不能动手 | 它自己（被点的东西消失/变了） | 这个动作的名字 |
| 动作链 | 能不能动手 | 下一个节点 | 最后停住的节点 |
| 守卫 `Ensure` / `Branch` | 到没到 | 守卫里的探针 | 卡住那个页面的名字 |

三条判据同时成立才用自环动作：

- **识别的是"能不能动手"，不是"到没到"**（`Ensure` 判的正是后者）。
- **点完它自己就不再命中**：按钮消失、弹窗关掉、按钮变暗。
- **不需要"卡在哪个页面"这个信息**。

自环的出口是"自己不再命中"，所以它必须配有限 `timeout`，禁止 `timeout: -1`；到点判失败即可，`on_error` 只放必须的收尾。

点完那个东西还在（切页签、开关、按住、状态变了框还在），自环会一直点下去：这种情况只能写守卫。守卫段要自停，候选里不能再放"自己还会往下走"的转发节点——它的 `next` 跑完就重来一轮，守卫永远等不到画面变化。

**什么时候才写 `Loop`（废弃）**：新代码用 `Branch` 代替。既有 `Loop` 的判据：父级守卫不能自己重跑（它是入口或终局），或者这一段有自己的固定出口（守卫失效、有限 `timeout`）。单独成页、父级又能重试的活，直接排在父级候选里。

### `Loop` 末尾的兜底 `Ensure`

`[JumpBack]` 回跳只回到父节点的 `next` 重扫，父节点自己的 `recognition` 与 `action` 都不重跑，所以 `Loop` 察觉不到"已经离开这页"。它只能在"候选全部 miss"时反应，而这件事有两种含义：

| 全 miss 的含义 | 放兜底 `Ensure` 的效果 |
| --- | --- |
| 画面漂走了 | 正确：拉回来继续 |
| 活干完了（守卫随工作消失） | 错误：把完成态当故障，重新拉回工作态 |

判据：**这个 `Loop` 的完成态有没有候选接得住。** 有就放；没有（完成只能表现为全 miss）就先补一个完成候选，再放兜底。

兜底的探针不能与本 `Loop` 的守卫探针相同（方向相反也算）：那等于把"守卫不成立"修成"守卫成立"，循环永远不结束。

## 四、`[JumpBack]` 放在哪

`[JumpBack]` 标的是**引用处**，不是节点属性。同一个节点在 A 处是候选位、在 B 处可能是顺序位，两者都对：

| 位置 | 含义 | 该不该标 |
| --- | --- | --- |
| 候选位 | "这件事必须先办成，办完弹回我这里继续" | 必须标 |
| 顺序位 | "顺手往下走，不在我就试下一项" | 不标 |

四条落地规则：

1. **回上级 / 回枢纽（`Ensure`）一律当候选位**，引用处都写 `[JumpBack]`。这类节点跑完要弹回调用方的 `next`，由调用方决定下一步；它自己不许串到别的任务的主循环。
2. **页内进入（就位 → 工作）是顺序位**，不标 `[JumpBack]`，靠 `next` 自然遍历过去。
3. **同任务内可以 `[JumpBack]` 指向子 `Loop`**，语义是"先把这段工作干完，再弹回父 `Loop` 继续"，用于一页里多段独立工作的串行推进（`TrainLoop` → `[JumpBack]TrainLoopReward` / `[JumpBack]TrainLoopAcceptable`；`TaskGift.next` → `[JumpBack]GiftLoopChoose`）。仍然禁止：指向自身（那就是普通的自循环候选）、指向自己的祖先 `Loop`（弹回层次会绕圈）、指向别的任务的 `Loop`。
4. 除规则 3 的子 `Loop` 外，`[JumpBack]` 的落点只放动作节点和探测节点，这样每次弹回哪一层都能从名字读出来。

## 五、预算

- `max_hit` 是"一整个 task 内命中多少次"，只给**任务级导航**（从枢纽到页面）。不要在循环自愈路径上依赖它——命中耗尽时框架只是**跳过候选**，不报错，症状是任务在别处莫名失败。
- 循环自愈路径上确实需要 `max_hit` 时，只允许这两种形态，并在节点注释或文件头写明理由：
  - **agent 侧显式复位**：写了 `max_hit: N`，同时有 `context.clear_hit_count("<节点名>")` 在合适的时机清零（`TrainMoveToBottom` 的 `max_hit: 1` 配 `TrainLoopAcceptableReco` 的复位）；
  - **明确的限次**：这次任务本来就只该做 N 次，且 N 次用尽后链上有别的候选接管，不会留成"静默跳过"。
- 循环内需要重复做的事**不设计数兜底**，出口只有两条：
  - **守卫失效**：`recognition` 不再命中 → 该节点判失败、弹回调用方，等于替调用方做了一次探测。这是首选出口，页面上"已经做完/已经离开"的判据都该做成守卫或候选。
  - **有限 `timeout`**：到点判失败，框架报 `Task timeout [pretask.name=<节点名>]`。`on_error` 只放**必须做的收尾**（松手、关弹窗、复位状态），这一层不需要收尾就不要写——失败本身就是合法出口，补一条 `focus` 把原因说清楚即可。
- 为什么不用"连续未命中计数"兜底（本仓库曾用 `LoopErrorByTimes`，2026-10 决定删除）：
  - **拦不住卡死**：节点 `next` 含自身时，自循环那轮自身命中，外层计数轮不到；样本是 `EscortClickOk` 用同一个 `box=[1005,522,64,37]` 连点 8 次、26.9 s 而任务既不失败也不结束。
  - **静止画面上反而误杀**：所有候选都 miss 的等待页上，计数按约 1 轮/秒连刷，2026-10-10 `21:46:25.94→21:46:34.95` 九秒十轮把任务判失败，而同期 20 场代理其实已经跑完。
  - **报错信息更差**：计数走 `TaskStopError` 只留一句"loop异常 结束任务"；`timeout` 直接给出卡住的节点名，配合 `debug/on_error/<时间>_<节点名>.png` 就能定位。
- `timeout` 按**当前节点自己**算，入口节点的大 `timeout` 管不到下游。进入型节点按实际耗时收敛；循环节点用 `timeout: 30000` 一类的有限值，`-1` 只留给"守卫本身会在结束时失效"的等待型循环（例如"在战斗中"），并在节点注释里写明出口是守卫而不是超时。

## 六、命名对应

| 类别 | 命名 |
| --- | --- |
| 探测 | `<前缀>Probe<对象>` |
| 就位 | `<前缀>Ensure<对象>` |
| 工作（废弃） | `<前缀>Loop` |
| 通用就位 | `EnsureMain`（回大厅） |

`Ensure` 后面的对象是页面的短名，与 `Probe` 用的一致（`TrainingEnsureHome` / `TrainingProbeHome`）。就位节点内部需要的动作节点仍按动词表命名（`EnterBattleMainPage`、`ClickOk` 等）。

## 七、等次与枢纽

- 页面之间不是平级的：**枢纽页**（大厅、出击页）被多个任务共用，**等次页**（训练所、维修会、订单工厂、赠礼）只服务自己那条链。
- 从等次页回到枢纽是"降级"，用 `[JumpBack]<枢纽>Ensure` 表达；从枢纽进等次页是"进入"，用 `Ensure` 内部的进入动作。
- 枢纽类 `Ensure` 不许串到任何任务的主循环——它只负责"把人送回去"，去向由调用方的 `next` 决定。

## 八、待斟酌（写清判据，不做成校验规则）

### 出口节点是否匹配画面

`Custom` 识别返回的框决定了链往哪走，但"这个出口是否真的覆盖了画面上的分支"**没有静态判据**：同一个 `Custom` 识别在不同帧可能返回不同结果，工具只能看到"注册名有没有人用、名字对不对"。所以工具侧只保留两条能查的：注册名与节点名一致（`A3`）、注册名被引用（`A2`），其余靠人工。用 `Custom` 当 `Loop` 守卫或分支出口时，至少在注释里写清"返回什么代表什么"（形态选哪个见第三节「哪些活不用 `Loop`」）。相关：`A13-verb` 只能判"名字里有没有动词"，判不了"动作语义对不对"。

### `Init` 的两类

| 类型 | 特征 | 位置与命名 |
| --- | --- | --- |
| 真初始化 | 写全局变量、读参数、清计数（`TrainingInitAct` 读 `attach`、`ReplaysInitAct` 写 `_max_count`） | 放 `Task.next` 前段（`ProbeDaily` 之后）合理，`max_hit: 1` 也是对的 |
| 取状态再初始化 | 先识别一次状态再写全局（`TrainingGetStatusReco`、`TrainInitReco`） | **本质是探测**，按 `...Probe...` 命名；位置交给调用它的 `Ensure` / `Branch` 决定，不要顶在 `Task.next` 第一位挡住后面候选 |

这条只能人工判：一个动作节点到底"只是初始化"还是"顺便取状态"，工具看不出来。落到校验器上的只有 `A4-shadowed-candidate` 的提示——`Task.next` 里出现带 `max_hit` 的必然命中候选时，它后面的候选在额度用尽前不可达。

## 九、通用错误分支放哪

`BaseBranchError`（`base.json`）是"点掉挡路弹窗、留一份日志"的通用分支：中央弹窗区（ROI `320,148,636,423`）出现「确认」就命中，先判维护弹窗（`BaseBranchSeverClose` → `StopTask` 并弹通知），否则把弹窗标题与正文写进日志、点掉确认、等画面稳定，再弹回调用方继续。它**不判断"是不是错误"**，所以位置只影响"谁先抢画面"，不影响正常流程的语义。

### 放哪几类节点

只挂在有 `next` 的轮询节点上（`Task` / `Ensure` / `Branch` 的候选列表；`Loop` 已废弃），引用处一律写 `[JumpBack]BaseBranchError`。探测节点与单动作节点没有 `next`，它们的下一轮由调用方列表重新评估，不需要补。

```json
"next": [
    "<目标页正向探针>",
    "[JumpBack]BaseBranchError",
    "[JumpBack]<进入/回撤动作>",
    "<兜底候选>"
]
```

### 位次

四条判据从上往下判，冲突时前一条优先：

| 判据 | 为什么 |
| --- | --- |
| 自家流程会点「确认」的候选排在它**前面** | 同一个「确认」也会命中 `BaseProbeConfirm`；排在前面会抢点，并把正常流程记成"错误弹窗"（例：领奖流程里的"确认转换为零件"） |
| 会把"被压暗"读成状态的候选排在它**后面** | 模态弹窗下按钮模板常常仍命中、只是分数降低；"开始行动变暗＝合金不足"这类判据会被弹窗冒充 |
| 全取反守卫（`Ensure*`、顶层 `inverse: true` 的节点与终点探针）排在它**后面** | 弹窗挡住页面时取反守卫必然命中，会把"看不见"当成"不在页面"，带着弹窗去点入口或按钮 |
| 目标页的正向探针排在它**前面** | 页面正常就直接往下走，不必付这次识别 |

### 不要和专责的停止判断混排

`IsNoMetal` / `IsServerMaintenance` / `IsNetworkError` 是"判到就停"，`BaseBranchError` 是"点掉继续"。两类放在同一列表会互相抢顺序：同一个「确认」既可能被当成错误弹窗点掉，也可能被专责节点判成终止条件。维护弹窗尤其重复——`BaseBranchSeverClose` 与 `IsServerMaintenance` 都是 OCR「维护中」→ `StopTask`，接线时只留一处。

列表里已经有专门点确认的候选（`ClickConfirm`、`TrainOverrideConfirm` 这类）时通常不再加：它已经能点掉弹窗，再加只是多一次 OCR。要补的是这类列表之外的入口、就位与出口分支。

### 成本

命中评估一次＝一次 OCR（ROI 636×423）。按上表排在正向探针之后，只有前面候选全 miss 才付；排在前面则每轮都付。所以按"入口 + 就位 + 会把遮挡读成状态的分支"三处铺，不要每个节点都挂。

### 校验器能查的

`A15-error-branch-jumpback`（引用不带 `[JumpBack]`）、`A15-error-branch-shadowed`（排在取反守卫之后）、`A15-error-branch-conflict`（排在自己会点「确认」的候选之前）。"压暗被误读"那条判不了——哪个模板在弹窗下仍会命中，静态看不出来，按人工。

## 十、识别预算

一次派发的成本 = **守卫识别**（本节点的 `recognition`）+ **候选识别**（`next` 里被依次评估的项）。失败也要付钱，所以 `next` 的顺序与长度就是预算。

### 一次派发付几次识别

| 节点形态 | 守卫 | 每个候选 | 说明 |
| --- | --- | --- | --- |
| `DirectHit` | 0 | — | 不识别，白送 |
| `Probe`（单识别） | 1 | — | OCR / TemplateMatch / ColorMatch / Custom 各算 1 |
| `And` / `Or` 组合 | 子项之和（短路） | — | 命中即停，未命中才继续下一子项 |
| 候选是 `And[单探针]` 包装 | 1 | — | 包装本身不额外收费，但多一层事件 |

实测（16 份日志、28023 次派发）：`Loop` 平均 8.1 次、`Ensure` 6.8 次、`Task` 5.7 次、`Branch` 2.9 次。`Loop` 已废弃（见 §3），新代码用 `Branch`。

### `Ensure` 嵌套的成本

单层 `Ensure` 固定 5 次：守卫 1 + 首项探针 1 + 兜底 1 + 进入动作 1 + 末项（上一级 `Ensure` 或兜底）1。

嵌套时末项是上一级 `Ensure`，那一层再付 5 次，所以：

```text
深度 1 → 5 次   深度 3 → 14 次   深度 5 → 24 次
公式：5 × 深度 − 1（末层末项是 ReturnMain 而不是 Ensure）
```

实测最坏的是 `GiftEnsureRules`（深度 5，24 次）：它在 101 分钟的赠礼日志里被评估 593 次，是那次运行 12.2 分钟派发耗时的主要来源。

### 上限：`Ensure` 嵌套不超过 2 层

超过 2 层时改用 `Branch` 平铺（见下一条）。理由：第 3 层往上，每多一层就多 5 次识别，而它换来的只是「再往上退一级」；同样的效果可以靠调用方 `next` 里多排一个 `Branch` 候选达成，成本是 1 次。

### 页面导航：`Branch` 平铺优于 `Ensure` 嵌套

两种写法的语义不同，选哪个看**调用方需不需要「从任意页面保证到达 X」**：

| | `Ensure` 嵌套 | `Branch` 平铺 |
| --- | --- | --- |
| 语义 | 保证当前处于 X（不在就修，修不好退一级） | 在 X 就做 Y（不在就轮到下一个候选） |
| 结构 | `next` 末项指上一级 `Ensure`，形成链 | `next` 里只有工作候选，各 `Branch` 并列在调用方 |
| 全 miss 成本 | 5 × 层数 | 每个候选 1 次 |
| 命中成本 | 5 次 | 1 次守卫 + 工作候选 |
| 适合 | 枢纽页（大厅、出击页），多个任务共用 | 等次页（训练所、维修会、赠礼）自己的链 |

平铺写法：

```json
"TaskGift": {
    "next": [
        "[JumpBack]GiftProbeDaily",
        "GiftBranchSortPage",      // 在排序页 → 排序 + 点第一个
        "GiftBranchCharacters",    // 在选择页 → 点好感度
        "GiftBranchHome",          // 在赠礼主页 → 点赠礼
        "[JumpBack]BaseBranchError",
        "[JumpBack]ReturnMain"
    ]
},
"GiftBranchSortPage": {
    "recognition": "And",
    "all_of": ["GiftProbeRules"],
    "next": ["GiftChooseFavorability", "[JumpBack]BaseBranchError"]
}
```

每个 `Branch` 只判一个页面、只放该页面的工作候选。不在任何已知页面时依次 miss，落到 `ReturnMain`。

**判断顺序**：命中概率高的页面排前面（少付前面的 miss）。这与第九节「错误分支的位次」不冲突——`BaseBranchError` 仍排在正向探针之后。

### 首项探针只在守卫会误判时保留

`Ensure.next` 的首项通常是守卫里那个探针（「刚说不在，再问一遍」）。它的价值是纠正守卫误判，实测救回率差别很大：

| `Ensure` | 救回率 | 处理 |
| --- | --- | --- |
| `GiftEnsureRules` | 50% | 保留 |
| `FeiduEnsureHome` | 37% | 保留 |
| `GiftEnsureTavern` | 33% | 保留 |
| `EscortEnsureHome` | 25% | 保留 |
| `GiftEnsureHome` | 22% | 删 |
| `EntrustEnsureStage` | 9% | 删 |
| `TrainEnsureInfo` | 0% | 删 |

**判据**：救回率 < 25% 就删掉首项，把「确认」并进第一个进入动作的 `next`。救回率必须日志实测，不能凭感觉：在 `maafw.log` 里数这个 `Ensure` 作为派发者时首个候选的 `Node.Recognition.Succeeded` / `Failed` 次数，命中数 ÷ 总数就是救回率。

### 等待也是预算

`post_wait_freezes` / `post_delay` / `rate_limit` 不消耗识别，但占墙钟。实测 69% 的 `wait_freezes` 恰好停在 `time + rate_limit`，说明画面早已静止、等待是纯开销。

| 写法 | 什么时候用 |
| --- | --- |
| `post_wait_freezes` ≤ 1000 | 默认；下一轮候选的探针本身就是「到没到」的判据 |
| `post_wait_freezes` 2000–3000 | 只在页面切换动画确实超过 1 秒时用，并在注释写明是哪个动画 |
| 探针节点上不写 `post_delay` | 探针不改画面，延迟纯属限速；限速用所在 `Branch` / `Loop`（废弃）的 `rate_limit` |

`rate_limit` 是**每轮识别的最低间隔**，写在 `Branch` / `Ensure` 上比散在各个探针上更容易核对。

### 校验器能查的

| 规则 | 级别 | 判据 |
| --- | --- | --- |
| `A16-ensure-depth` | warn | `Ensure` 的 `next` 里指向另一个 `Ensure`，且从它算起嵌套深度 > 2 |
| `A17-guard-in-next` | info | 节点的 `next` 里含本节点 `recognition` 用到的同一个探针（重复识别） |
| `A18-next-length` | warn | `Task` / `Ensure` 的 `next` > 4 项，`Loop`（废弃）> 5 项 |

判不了的：救回率、动画实际时长、哪个候选命中率最高——都要日志实测（`debug/maafw.log` 里的 `Node.NextList.*` / `Node.Recognition.*` / `Node.WaitFreezes.*` 事件流）。
