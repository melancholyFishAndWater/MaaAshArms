# 解析口径（读图前先看这里）

日志里有什么就画什么。以下几条决定了图上的字面含义与"为什么少了/多了某几步"。

- **父节点的来源**：`Node.NextList.Starting/Succeeded/Failed` 事件（`name` = 正在评估 next 表的节点、
  `list` = 那一刻排着的候选）。它是**调用图不是树**；套框与配色见 [layout.md](./layout.md)。
- **"卡在派发层"要点名**（图第二行 + `--list` 末尾的「父节点评估」账）：`Node.NextList` 分三种事件——
  `Starting`（开始评估）、`Succeeded`（有候选命中）、`Failed`（整张候选表一个都没命中）。
  **同一条候选表连续 `Failed` 就是"任务一直重试候选、没有任何子节点跑起来"的直接证据**，而 `reco` 行
  不带 `task_id`，这是唯一能说清那段时间在干什么的数据。
  - 图上的注记形如「`TaskReplays` 的候选表 13 轮全未命中（候选 `ReplaysInit ・ …`），跑起来的候选：
    `LoopErrorByTimes`」；只报 `Failed ≥ 2` 的派发者（1 轮无命中是循环推进的正常现象），最多两条，
    且只在"图只涉及一个 task"时报。
  - `--list` 末尾追加 `--- 父节点评估（Node.NextList）---`：按派发者列出 `未命中 N 轮 / 开始 N /
    命中 N` 与**真实候选表**（取全未命中那一轮的 `list`——入口轮是 `[自己]` 的自派发，不能当候选表）。
  - 实测（`PYTHON-J`，task 200000167）：只有 2 条 `PipelineTask node done`，但 `TaskReplays` 的候选表
    **13 轮全未命中**、`LoopErrorByTimes` 随后 → `BaseTaskStopError`——旧版图只看得到末尾两步。
- **按时间重排**：日志时间戳回跳时（Explore 导出的 CSV 是分块拼接的）先按时间戳稳定排序再解析，
  图上印一行「日志时间戳有回跳，已按时间重排（N 行）」。不再有"遇到第一条晚于 `--to` 的行就停"这一步——
  它会把窗口内的记录整段丢掉，还报成"窗口内没有记录"。
- **仅事件模式**：日志里没有 `PipelineTask node done`（Sentry 导出就是这种）时，用识别记录
  （`reco [result=]`）合成步骤，图上印「由识别记录还原」。此时默认按 `--collapse` 把连续同节点的
  识别折成一格（`未命中 ×13`）；`--collapse 1` 保留每次识别各占一列。`reco` 行里没有 `task_id`，
  能取到该 task 的起始行就夹住范围，取不到会印一行提示。
  **取不到范围、而日志里又看得出是别的 task**（`Node.NextList` / 任务事件带 task_id，且一条都不属于
  这个 task）时**不合成**：这段识别记录全属于别的任务，硬画出来就是同一份"全任务混在一起"的日志
  （实测 `PYTHON-33/35/36` 的包只留了 MFA 面板行，三张图除了标题一模一样）。调用方会因此退概览卡。
- **派发链模式**（再退一步）：日志里连 `reco` 行都没有、只剩事件总线时（Sentry 有时只留这一段：
  实测 `PYTHON-31` 的包在失败的那 95 秒里只有 `Node.*` 事件），用该 task 的 `Node.NextList.*`
  派发记录还原——**一个派发者一步**，按第一次派发排成一条链，图上印「由 NextList 派发记录还原」。
  能还原的只是"依次派发了哪些节点"，不是完整执行顺序；候选表一次都没成功过的那个节点画成
  「未命中」（`kind=miss`），"卡在派发层"的候选表账照常由 `stall_notes` 出。父节点按链上前一步
  推出来（`parent_source=chain`，单列记账，不算进"父节点没找到"）。
- **`--task-id` 严格过滤 + 任务判定窗口**：`steps` 与事件都按 `task_id` 过滤；框架级事件
  （`Task timeout` / `invalid node id` / `node not completed`，没有 `task_id`）改用**判定窗口**归属——
  下界是本任务第一步，上界优先取**它自己的 `task end`**（任务失败后框架不再为它记东西），
  没有 `task end` 时退回"本任务最后一步之后、别的任务的第一步"。未命中聚合（`reco` 行同样没有
  `task_id`）用同一个窗口。这样一份装了多次运行的日志不会把 23:59 那趟训练的未命中画进 13:11 那趟
  维修的末轮，也不会把同一运行里后一个任务的超时画进前一个任务的图上；而"最后一步之后"的失败标记
  仍留在图上（任务失败恰恰发生在最后一步之后）。被排掉的条数会印出来。
- **任务号在各进程内复用，`--task-id` 要配 `--pid`**：MFA 每次启动都从同一个基数重新分配任务号
  （本机 `maafw.log` 里 `200000001` 同时出现在 `Px15316`（18:01）与 `Px6448`（20:40）两次运行下）。
  只给 `--task-id` 会把这几次混成一张图——**步骤数对不上就是它**。先 `--list-tasks` 看清单：

  ```powershell
  python tools/drawing/cli.py flow <安装根>/debug/maafw.log --list-tasks
  # 进程      task_id  步数  开始                    结束                    入口
  # Px15316  200000001     1  2026-10-27 18:01:14.527 2026-10-27 18:01:15.337 @mse/action
  # Px6448   200000001     5  2026-10-27 20:40:35.535 2026-10-27 20:40:56.080 TaskEscort
  ```

  再 `--pid Px6448 --task-id 200000001`。不给 `--pid` 时保持旧行为（只按编号切，全文混合）。
  `--list-tasks` 只列有节点执行的任务；`MaaTaskerPostStop` 那种 0 步的停止指令不列。
  `cases` 也接受 `--pid`（透传给 `FlowOptions.px`），产物名会带上 `_px<进程>`：
  实测 `maafw.bak.2026.11.02-08.57.51.341.log` 里 `200000003` 同时属于 `Px12748` 与 `Px3352`，
  不给 `--pid` 是 16 步、给 `--pid Px3352` 是 9 步。
- **诊断注记**：由上面这些事实构成的注记印在图第二行，**一条一行、按类型上色**并同时打到 stderr。
  绿 = 这次用的资源版本；琥珀 = 疑似过时 / 记录被裁断；红 = agent 缺位；蓝 = 由识别记录 / 派发记录还原；
  紫 = 时间戳回跳；灰 = 其他前提。

判据都写在代码里：`round_steps()`、`compose_columns()`、`describe_empty_window()` 的文档字符串。
